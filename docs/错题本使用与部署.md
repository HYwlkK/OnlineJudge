# QDUOJ 错题本使用与部署

完成部署后，原 OJ 顶部导航栏中会出现“错题本”。用户登录后点击它，可以查看自己在 OJ 普通练习中做错的题目。没有错题时显示“暂无错题”。

## 数据规则

- 数据来自原有 `problem` 和 `submission` 数据表。包含已有的普通练习提交和之后的新提交。
- 编译错误、答案错误、运行错误、时间超限、内存超限和部分通过计入失败；等待、判题中、系统错误及完全通过不产生错题。
- 同一道题只显示一次，列出本人失败次数、最近失败和最近提交结果。后来通过的题目保留失败历史，并显示最近结果“通过”。
- 比赛提交不纳入本版。隐藏、删除的题目不显示；普通用户和管理员都只能查看本人的错题。
- 判题或重判结果变化后，重新打开错题本或点击“刷新”即可更新；若全部失败提交被重判为通过，该题从列表移除。
- 点击题目进入原 OJ 题目页继续提交代码；点击最近失败结果进入原 OJ 提交详情。

本功能只查询 OJ 数据库，没有访问用户电脑文件的接口，也不需要新建错题数据表。

## 修改范围

后端新增 `submission/views/wrong_problem.py`，在 `submission/urls/oj.py` 注册 `GET /api/wrong_problems`。参数是 `offset`（默认 0）和 `limit`（默认 20，最大 100）；返回 `{error: null, data: {total, results}}`。

原项目的 Dockerfile 只下载已编译前端，因此单改 Python 无法在导航栏新增菜单。本次将它改为编译同版本的 OnlineJudgeFE Vue 源码，并应用 `frontend` 目录中的导航、路由和页面修改。接口数据由服务器按登录用户取得，不接受客户端指定数据所属用户。

上一轮独立 Django 页面、复习标识、复习计划、独立数据表迁移和补偿进程的代码已撤销。原判题、提交、Nginx 和 Supervisor 的行为恢复原状。

## 在已有 Linux Docker 部署中启用

将修改后的 `OnlineJudge-master` 放到运行 OJ 的 Linux 虚拟机。在该项目目录构建镜像：

```sh
docker build -t qduoj-wrong-problems:local .
```

在你现有的部署 Compose 文件中，将 **OJ 后端服务** 的 `image` 改成 `qduoj-wrong-problems:local`，保留该服务现有的数据库、Redis、判题服务配置和数据卷。上游部署通常将此服务命名为 `oj-backend`，以你实际的服务名为准。然后在部署 Compose 所在目录运行：

```sh
docker compose up -d --no-deps oj-backend
```

如果使用旧版命令，则使用 `docker-compose`。如果服务名不是 `oj-backend`，替换为实际名称。

最后打开原来的 OJ 网址，强制刷新浏览器，导航栏“题目”旁边会出现“错题本”。地址仍在原 OJ 站点内，例如 `http://原OJ地址/wrong-problems`。

这一功能不需要额外执行新增表迁移。当前电脑没有连接你实际运行的 OJ，此处修改源码和构建配置不会自动更新虚拟机中的运行实例。

## 验证

后端测试使用独立的内存数据库和模拟任务队列：

```sh
python manage.py test submission.test_wrong_problems --settings=oj.test_settings
```

测试覆盖空列表、判题结果分类、同题去重、通过后的展示、用户隔离、匿名与停用账号、隐藏/删除题目、比赛隔离、重判、结果顺序及分页校验。

本次本地验证：15 项后端测试全部通过；原版 Vue 前端生产构建成功；使用 Edge 156.0.4314.58 对编译产物验证了导航入口、空状态、直接刷新、列表与结果标签、原题和提交链接、错误提示、分页、尾页清空后恢复、返回题库及匿名登录拦截。浏览器验证使用隔离的接口测试数据，未连接实际运行的 OJ。Linux Docker 镜像及真实 PostgreSQL、Redis、JudgeServer 联调仍需在部署环境验证。

在你的运行实例中，可以用测试账号验证：无提交时进入错题本为空；普通练习提交错误程序后出现该题；重复失败仍只显示一题；换账号看不到前一个账号的错题；点击题目能够返回原题继续作答。
